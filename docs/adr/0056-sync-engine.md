# ADR-0056: The sync engine

- Status: Accepted (P04 task T3, 2026-11-14)
- Date: 2026-11-14
- Deciders: Implementation, within the owner's decisions D6, D7, D9, D10 of [p04-plan.md](../roadmap/p04-plan.md)
- Related: [ADR-0015](0015-per-type-conflict-resolution.md), [ADR-0052](0052-sync-backend-and-end-to-end-encryption.md), [ADR-0053](0053-sync-storage-contract-schema-v10.md), [ADR-0055](0055-sync-server-port-and-contract.md), [sync-protocol.md](../data/sync-protocol.md), spike S-04

## Decision
1. **Push.** Every record a pending outbox row names is read as it is now, sealed (with its kind, id and schema version inside) and pushed with the version last synced as its base, in batches of 500. The operation id is a UUID v5 of (device, kind, id, version), so a retry after a lost answer is the same operation and the server stores it once (SYNC-001). Accepted: the copy becomes the last synced one (`sync_base`, with its server id) and its outbox rows are acked. A conflict is left pending. A refused batch is split until the one record the server will not take is found; that record's rows are set aside as `failed` and the rest goes on. Outbox rows of things that never sync (a profile, a sync batch) are marked `local`.
2. **Pull.** The server's changes after this device's cursor, page by page. A record this device has not changed since the last sync is taken as it is; one it changed too is merged by `mergeRecord` (domain, pure): task fields one by one with a task's status never going down; schedules, reminders, exceptions, period results, sessions and workspace settings as one value with the other value kept for review; notes as one value with a review; measurements and execution records append-only; an occurrence tick never undone; a delete beats an edit or a restore, the edits stay in the trash, with a review (D6, D7). Ties go to the later update, then the device name, so devices that both merge reach the same record. A record the server purged is deleted here too (GS-14). A record that cannot be opened becomes an `unreadable` review item.
3. **Through the gateway.** Each page is one command, `ApplySyncChanges`, of actor `sync` (the device id) through the gateway (GOV-001, FF-ARCH-06/09). Its records, their last synced copies, their outbox rows (acked when taken from the server, pending when merged), the review items and the new cursor commit together, so a page is applied whole or not at all and the cursor never passes what the store holds. The `sync` actor may run only this command, only for a workspace this device syncs, only under this device's id.
4. **Changes to review.** `sync_reviews` (schema v11; device bookkeeping, not exported, not synced) keeps each value that gave way: the kind, the record, the field, the kept and the other value, the reason. T5 shows them.
5. **Newer versions (D10).** A change of a kind, or of a schema, this app version does not know stops the pull at that change with the outcome `updateNeeded`; nothing after it is skipped, and pushing still works.
6. **Retries.** A sync reports `upToDate`, `offline` (no connection, a paused server, a lost answer), `signedOut`, `notYours`, `updateNeeded` or `failed`, and stores it in `sync_state`. Nothing is lost on a failure: the outbox stays pending and the cursor where it was. `syncBackoff` gives the waits between tries (5 s, 15 s, 1 min, 5 min, then 15 min) for the scheduler of D8 (T5). Each sync also asks the server to purge records deleted more than 90 days ago.

## Consequences
- Schema v11: `sync_reviews`, `sync_base.server_id`. Stores from v2–v10 upgrade with every column checked.
- **Every future schema step must say how a pulled record of the previous schema is read**, as the export does for files; today every syncing device is on v10 or later, and a record that cannot be read becomes a review item.
- The S-04 prototype (`test/sync_spike/`) is replaced by the engine and its tests.
- Tests: `sync_merge_test.dart` (domain, 8, with a 2000-case property that either device merging gives the same record), `sync_engine_test.dart` (14: GS-17 with a lost answer, the server seeing no content, SYNC-003 cases, Changes to review, D7, append-only, GS-14, offline and signed out, a refused record set aside, pages, D10, a page not half-applied, the sync actor's limits, a property run of 8 seeds × 40 random edits and syncs on three devices), the apply step in `atomic_set_test.dart`, the end to end of `sync_keys_test.dart` now on the engine. Mutations 11 of 13 killed (the deterministic operation id after the replay test was made to check the change numbers); the 2 that survive change nothing observable: a merged record also keeps its earlier pending outbox row, and an accepted record's rows are acked again on the next round.
